# База данных

SQLite, файл `%APPDATA%\com.easypl.app\easy-pl.db`, доступ через
`tauri-plugin-sql`. Схема создаётся и обновляется миграциями при первом
обращении к базе — отдельного шага установки нет.

## Таблицы

### Справочники

**`classes`** — классы и ветки. `id`, `base_name`, `path`
(`succession`/`awakening`/`liberation`/`none`), `display_name`, `is_active`,
`sort_order`, `uid`, `updated_at`. Уникальна пара `(base_name, path)`.
`display_name` отдельно от `base_name`, чтобы админ мог переименовать под себя.

**`raids`** — рейды. `id`, `name` (уникально), `is_active`, `sort_order`, `uid`,
`updated_at`.

**`players`** — гильдия. `id`, `family_name` (уникально), `class_id`, `raid_id`,
`discord`, `discord_id`, `joined_at`, `debt`, `is_favorite`, `note`, `uid`,
`updated_at`. `raid_id` необязателен — «без рейда» это нормальное состояние.

### Осада

**`events`** — событие. `id`, `title`, `event_date`, `slots`, `reserve_size`,
`seed`, `share`, `status` (`draft`/`drawn`/`closed`), `uid`, `updated_at`.

`slots` — **производная** сумма квот, её держит `refreshTotalSlots`;
пользователь вводит места по рейдам, а не общее число. `share` осталось запасом
для клиентов старой версии: настоящая доля живёт в квоте рейда.

**`event_quotas`** — места по рейдам. `(event_id, raid_id)` — первичный ключ,
`slots`, `share`. Ноль в `raid_id` означает «без рейда»: `NULL` в составном
ключе SQLite уникален каждый раз, и две строки `(event_id, NULL)` прошли бы
молча. Поэтому там суррогатный ноль, а не внешний ключ.

Строки с нулём мест не хранятся: отсутствие строки и `slots = 0` для жеребьёвки
одно и то же, а не-хранение оставляет неиспользованный рейд удаляемым.
Исключение — розыгрыш: он пишет строку и для группы с нулём мест, чтобы у её
участников был свой `share = 0`.

**`event_signups`** — заявки. `(event_id, player_id)`, `is_priority`, `raid_id`.

`raid_id` здесь — **разовый рейд на эту осаду**, `NULL` значит «в своём».
Постоянный рейд игрока при этом не меняется: справочник описывает состав
гильдии, а не расстановку на один вечер.

**`event_slots`** — состав. `(event_id, player_id)`, `source`
(`priority`/`lottery`/`fallback`/`manual`), `reserve_rank`.

**`attendance`** — явка. `(event_id, player_id)`, `showed_up`, `marked_at`.

**`draw_log`** — снимок жеребьёвки. `event_id` (PK), `seed`, `snapshot_json`,
`created_at`. В снимке — веса, ключи и группы на момент розыгрыша: по нему
результат можно пересчитать и доказать, что никого не обошли.

### Служебные

**`settings`** — `key`/`value`, строки:

| Ключ | Значение |
| --- | --- |
| `sync.url` | адрес сервера синхронизации |
| `sync.revision` | до какой ревизии сервера дочитали |
| `sync.syncedAt` | когда последний раз собирали свои правки |
| `sync.preset` | отпечаток связки из `.env`, чтобы применить её один раз |
| `discord.guildId`, `discord.emoji` | сервер и эмодзи заявки |
| `ui.theme` | выбранная тема |

**`tombstones`** — надгробия: `(entity, uid)`, `deleted_at`. Без них удаление на
одной машине воскресало бы при обмене с другой.

**`uid_aliases`** — `(entity, old_uid)` → `new_uid`. Когда чужая запись
опознаётся по естественному ключу и усыновляет локальную, старый uid остаётся
здесь, чтобы ссылки из старых пакетов продолжали резолвиться.

**`_migrations`** — `version`, `name`, `applied_at`.

## Эффективный рейд

Группа игрока **на осаде** — это `COALESCE(s.raid_id, p.raid_id, 0)`, где `s` —
`event_signups`, `p` — `players`. Ноль — «без рейда».

Любой запрос, который считает места, заявки, «вне жребия», состав, явку, долю
рейда или статистику, обязан джойнить `event_signups` и брать эту величину.
Возьмёте `p.raid_id` — разово выведенный игрок попадёт в свою группу, и квоты
разъедутся с составом: у принявшего рейда человек в составе, а места ему
посчитаются в другом месте.

Удаление рейда сбрасывает эти отметки вместе с квотами (`dropRaidFromEvents`),
иначе останется группа с мёртвой ссылкой и пустым названием.

## Миграции

`src/db/migrations.ts` — массив `MIGRATIONS`, у каждой номер, имя и список
запросов. `runMigrations` пропускает применённые по журналу `_migrations`.

Правила:

- **Только добавлять.** Применённая миграция не редактируется никогда: у людей
  она уже прошла, и правка до них не доедет.
- **Идемпотентность.** `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT
  EXISTS`, `INSERT OR IGNORE`. Для `ALTER TABLE ADD COLUMN` идемпотентности нет,
  поэтому у таких запросов есть `skipWhen` с проверкой по `pragma_table_info`.
  Журнал — основная защита, идемпотентность — страховка на случай прерванной
  миграции или ручного вмешательства.
- **Ошибка заворачивается в `MigrationError`** с номером и текстом запроса,
  иначе в проде видно только «SQL error» без места падения.
- **Каждое изменение схемы покрывается тестом** в `migrations.test.ts`: там
  настоящий SQLite, и другого способа поймать сломанный DDL до установки нет.

Сид (классы, состав гильдии) — тоже миграции. У сид-записей `uid` выводится из
естественного ключа (`class:Ведьма:succession`), а не случайный: две свежие
установки должны получить одинаковые идентификаторы, иначе справочник
задвоится. Отметка времени у сида фиксированная, а не момент установки, — иначе
свежая установка выглядела бы новее всех и откатывала чужие переименования.

## Правила работы с базой

**Массовая запись — одним запросом.** У плагина нет транзакций, а `BEGIN`/
`COMMIT` отдельными вызовами ненадёжны: пул соединений, и `COMMIT` может уйти не
в то соединение. Поэтому `INSERT ... VALUES (…), (…)` и
`UPDATE ... SET x = CASE id WHEN … END WHERE id IN (…)` батчами по 100 строк.
Цикл из отдельных `UPDATE` — это автокоммит с fsync на каждую строку: 120 строк
по одной занимают ~300 мс против ~2 мс одним запросом.

**Каскады `ON DELETE` не работают.** `PRAGMA foreign_keys` действует только на
то соединение, где выполнен, а соединение из пула достаётся случайное. Внешние
ключи в схеме остаются документацией и страховкой в тестах, а удаление связанных
строк пишется явными запросами в репозитории.

**Права на запись прописаны отдельно.** `sql:default` — это только `allow-load`,
`allow-select`, `allow-close`; `sql:allow-execute` добавлен в
[capabilities/default.json](../src-tauri/capabilities/default.json). Симптом
отсутствия обманчивый: файл базы создаётся, ошибок нет, а первый же DDL молча
отбивается правами.

**Отметка времени — полный ISO-8601 с `Z`** (`new Date().toISOString()`). Голая
дата `2026-08-09` в лексикографическом сравнении встаёт раньше любой отметки
того же дня, а сервер такие значения отклоняет целиком — один кривой формат
заваливает весь обмен.
