# easy-pl — учёт явки на осады

## Постановка

Приложение ведёт учёт участия гильдии в событиях с ограниченным числом мест.

Администратор создаёт событие (осаду), указывает количество слотов и отмечает
игроков, которые обязаны попасть. Оставшиеся слоты разыгрываются жребием так,
чтобы за длинную дистанцию все побывали на осадах примерно одинаковое число раз:
кто не прошёл в прошлый раз, в следующий имеет больший вес.

Состав гильдии меняется — игроки приходят и уходят, это не должно ломать расчёт
справедливости.

По итогу события отмечается, кто фактически пришёл, а кто нет.

## Модель данных

SQLite локально (`tauri-plugin-sql`), синхронизация — отдельным слоем поверх.

```sql
settings(key TEXT PRIMARY KEY, value TEXT)

classes(
  id            INTEGER PRIMARY KEY,
  base_name     TEXT NOT NULL,
  path          TEXT NOT NULL,          -- succession | awakening | none
  display_name  TEXT NOT NULL,
  is_active     INTEGER NOT NULL DEFAULT 1,
  sort_order    INTEGER NOT NULL DEFAULT 0,
  UNIQUE(base_name, path))

raids(                                  -- справочник рейдов
  id            INTEGER PRIMARY KEY,
  name          TEXT NOT NULL UNIQUE,
  is_active     INTEGER NOT NULL DEFAULT 1,
  sort_order    INTEGER NOT NULL DEFAULT 0)

players(
  id            INTEGER PRIMARY KEY,
  family_name   TEXT NOT NULL UNIQUE,
  class_id      INTEGER REFERENCES classes(id),   -- необязателен
  raid_id       INTEGER REFERENCES raids(id),     -- необязателен
  discord       TEXT,
  joined_at     TEXT NOT NULL,
  debt          REAL NOT NULL DEFAULT 0,
  is_favorite   INTEGER NOT NULL DEFAULT 0,
  note          TEXT,
  updated_at    TEXT NOT NULL)

events(
  id            INTEGER PRIMARY KEY,
  title         TEXT NOT NULL,
  event_date    TEXT NOT NULL,
  slots         INTEGER NOT NULL,
  reserve_size  INTEGER NOT NULL DEFAULT 0,
  seed          TEXT,
  share         REAL,
  status        TEXT NOT NULL,          -- draft | drawn | closed
  updated_at    TEXT NOT NULL)

event_signups(                          -- кто планирует прийти
  event_id      INTEGER NOT NULL,
  player_id     INTEGER NOT NULL,
  is_priority   INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY(event_id, player_id))

event_slots(                            -- результат жеребьёвки
  event_id      INTEGER NOT NULL,
  player_id     INTEGER NOT NULL,
  source        TEXT NOT NULL,          -- priority | lottery | manual
  reserve_rank  INTEGER,                -- NULL = основной состав
  PRIMARY KEY(event_id, player_id))

attendance(                             -- факт явки
  event_id      INTEGER NOT NULL,
  player_id     INTEGER NOT NULL,
  showed_up     INTEGER NOT NULL,
  marked_at     TEXT NOT NULL,
  PRIMARY KEY(event_id, player_id))

draw_log(                               -- снимок для проверки жребия
  event_id      INTEGER PRIMARY KEY,
  seed          TEXT NOT NULL,
  snapshot_json TEXT NOT NULL,
  created_at    TEXT NOT NULL)
```

Разделение `event_slots` и `attendance` принципиально: «получил слот» и «пришёл»
— разные факты, и весь смысл штрафа за прогул держится на этой разнице.

## Жеребьёвка

### Долг

У игрока есть `debt` — накопленная разница между тем, сколько осад ему
причиталось по справедливости, и тем, сколько он реально отходил. Долг
накапливается только за события, на которые игрок заявился.

`share` — доля слотов на событии: свободные слоты, делённые на число участников
жеребьёвки (без приоритетных и без отсиживающих штраф).

| Событие | Долг |
| --- | --- |
| Новый игрок | `0` |
| Заявился, не попал | `+share` |
| **Прошёл по жребию — пришёл или нет** | `−(1 − share)` |
| Прошёл вне жребия и пришёл | без изменений |
| **Прошёл вне жребия и не пришёл** | `−2 × (1 − share)` |
| Не заявился | без изменений |

Вес в жребии — `max(0.25, 1 + debt)`. Долг ограничен `±10`.

Для прошедших по жребию явка на долг не влияет: очередь потрачена в любом случае.
Кто получил слот и не пришёл, тратит свой ход впустую и опускается в очереди
наравне с посетившими — отдельного флага штрафа для этого не нужно. Поправить
долг вручную можно прямо в списке гильдии.

Шаг `+share` / `−(1 − share)` подобран так, чтобы суммарный долг не дрейфовал ни
при каком соотношении слотов к желающим: математическое ожидание изменения за
событие равно нулю. Это принципиально — при фиксированном шаге `±1` и отборе
25% долг у всех инфлирует, упирается в кап, веса выравниваются и жребий
вырождается в равномерный.

**Прошедшие вне жребия** — это приоритетные (`source = 'priority'`) и заменившие
не пришедшего (`source = 'manual'`). Они не участвовали в розыгрыше свободных
мест, поэтому явка им долг не меняет: место досталось не за счёт очереди, и
списывать за него нечего.

Прогул — другое дело. Место они всё-таки заняли и потратили впустую, причём
гарантированное, поэтому списание идёт **вдвое от обычного**: `−2 × (1 − share)`.
Это единственный случай, когда явка влияет на долг, и он же закрывает вопрос
дисциплины без отдельного флага штрафа.

### Проверка на симуляции

Разброс явки (`max − min`) за длинную дистанцию, 20–60 игроков:

| Модель | 200 событий, 10 из 20 | 200 событий, 10 из 40 | 100 событий, 20 из 25 |
| --- | --- | --- | --- |
| Счётчик пропусков со сбросом | 20 | 15 | 14 |
| Долг с шагом `share` | **2** | **2** | **2** |

Тесты в `src/lottery/draw.test.ts` держат разброс ≤ 4 на четырёх конфигурациях.

### Розыгрыш

1. Приоритетные игроки занимают слоты вне жребия. Если их больше, чем слотов —
   ошибка, админ правит вручную.
2. Свободные слоты `free = slots - priority` разыгрываются среди остальных
   заявившихся.
3. Взвешенная выборка без возвращения по методу Эфраимидиса–Спиракиса:
   для каждого кандидата `key = u^(1/tickets)`, где `u ~ U(0,1)`; берутся `free`
   кандидатов с наибольшим ключом. Один проход, корректные пропорции.
4. Тем же способом добираются `reserve_size` резервистов.
5. Тикеты пересчитываются по таблице выше.

Генератор псевдослучайных чисел — детерминированный (mulberry32) с сохраняемым
`seed`. `Math.random()` не годится: жребий должен быть воспроизводим, чтобы любой
участник мог пересчитать результат и убедиться, что его не обошли. В `draw_log`
кладётся снимок весов на момент розыгрыша.

Резерв поднимается вручную при неявке кого-то из основного состава.

### Смена состава гильдии

Вышедший из гильдии удаляется из базы полностью — состояния «вышел» нет.
Вместе с игроком явными запросами вычищаются его строки в `attendance`,
`event_slots` и `event_signups`, поэтому его участие в прошлых осадах из
статистики пропадает. Это осознанный размен: справочник остаётся чистым,
исторические сводки по закрытым событиям становятся неполными.

Вернувшийся заводится заново и начинает с `debt = 0`, как любой новичок.

Долг меняется только за события, на которые игрок заявился, поэтому перерыв в
участии сам по себе ничего не накапливает — это решается моделью, а не
отдельной заплаткой.

### Контроль справедливости

В таблице игроков — колонки «посещаемость» (`пришёл / заявлялся` за последние N
событий) и текущий долг. Перекос виден сразу, без разбирательств.

## Рейды

Отдельный справочник, редактируется в настройках. Игрок может состоять в рейде,
а может и не состоять — `raid_id` необязателен. Удалить рейд, назначенный
игрокам, нельзя: его можно только отключить, иначе поедут ссылки.

Хранится ссылка на запись справочника, а не строка: при переименовании рейда
у всех игроков подпись меняется сама.

## Классы

Модель — `base_name` + `path`, где `path` это `succession` (Традиция),
`awakening` (Пробуждение) или `none`. Каждая комбинация — отдельная запись, на
неё и ссылается игрок. `display_name` хранится отдельно, чтобы админ мог
переименовать («Ведьма Трад» вместо «Ведьма (Традиция)»).

Справочник редактируется в настройках. `is_active` позволяет скрыть ненужное, не
удаляя (иначе поедут ссылки в истории).

Сид сверен с официальным сайтом (`ru.playblackdesert.com/GameInfo/Class`,
проверены карточки всех 32 классов, август 2026). Веток три, и набор у классов
разный:

| Набор | Классы | Кол-во |
| --- | --- | --- |
| Традиция + Пробуждение | все остальные | 25 |
| Пробуждение + Освобождение | Вуконг, Лучник, Мертвый Глаз, Сераф, Сколария, Шай | 6 |
| Только Традиция | Агент | 1 |

Освобождение — это ветка тех классов, у которых нет Традиции, а не третья
дополнительная. У Агента (вышел 30 июля 2026) пока нет Пробуждения: новые классы
получают Традицию летом, а Пробуждение зимой, — при выходе ветку надо добавить
руками в настройках.

Итого 63 записи. Сид ставится один раз при первом запуске и дальше правится в
настройках: игра меняется, и справочник должен переживать это без миграций.

## Состояния события

`draft` → `drawn` → `closed`, только вперёд.

- **draft** — набор состава. Можно отмечать заявившихся и приоритетных, менять
  параметры события. Жребий ещё не брошен.
- **drawn** — жребий проведён, состав зафиксирован. Заявки менять нельзя, можно
  отмечать явку. Пережеребьёвка стирает прошлый результат вместе с отметками.
- **closed** — долги пересчитаны по итогам, событие больше не меняется.

**Резерва нет.** Состав окончательный, а место не пришедшего может занять любой
заявившийся: кнопка «В состав» ставит его слот с пометкой `manual`. Запись
не пришедшего при этом остаётся — он слот занял и потратил впустую, поэтому
списание долга и скамейку получает наравне с посетившими.

Сверх лимита в состав не пустит. Занятыми считаются не все слоты, а только те,
чей владелец не отмечен как не пришедший: пока прогул не отмечен, место числится
занятым, и добавление отбивается ошибкой с прямой подсказкой — сначала отметьте
«Нет». Это и есть механизм замены: отметка освобождает место, и оно тут же
доступно любому заявившемуся.

**Избранные игроки** (`players.is_favorite`) поднимаются в начало списков, когда
не задан поиск, и автоматически получают «точно идёт» в момент заявки — на всех
путях сразу: ручная отметка, «заявить всех» и импорт из Discord.

Пересчёт долга происходит один раз, в момент закрытия. До этого отметки явки —
просто данные, на веса они не влияют.

Если все слоты заняли приоритетные игроки, `share = 0`: свободных мест не
разыгрывалось, и заявившимся впустую долг не начисляется — терять было нечего.
Сами приоритетные тоже остаются при своём, так что такая осада просто не влияет
на распределение.

Пункт 5 стоит держать чистой функцией: на вход список кандидатов с весами,
число слотов и seed, на выход состав, резерв и новые значения тикетов. Так он
тестируется, воспроизводится и переиспользуется при пересчёте задним числом.

## Открытые вопросы

- Квоты по классам при жеребьёвке — отложено, архитектура закладывается под них.
- Уважительная причина неявки (предупредил заранее) — сейчас не различается,
  любой невыход считается прогулом.
- Один админ или несколько одновременно — влияет на модель синхронизации.
