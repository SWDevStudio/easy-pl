# Синхронизация

Как компьютеры офицеров обмениваются данными без общего сервера в привычном
смысле. Разворачивание Worker'а, ключи Cloudflare и бот Discord —
в [sync-worker/README.md](../sync-worker/README.md); здесь — что происходит на
стороне приложения и почему.

## Модель

Нет клиент-серверной иерархии — есть N равноправных копий базы и один почтовый
ящик между ними (Cloudflare Worker + D1). Каждая копия:

1. отправляет свои изменения с последнего успешного обмена;
2. получает чужие, которые пропустила;
3. запоминает, до какой ревизии дочитала.

Всё, что синхронизируется (`classes`, `raids`, `players`, `events`), несёт
`uid` — локальные `id` автоинкрементные и на разных машинах столкнутся.

## Что летает пакетом

`collectChanges` ([src/sync/changes.ts](../src/sync/changes.ts)) достаёт из
базы всё, что изменилось с последнего обмена, и складывает в `Change`:

```ts
{ entity: "player", uid: "player:Kalimdor", updatedAt: "2026-08-09T12:00:00.000Z",
  deleted: false, data: { familyName, classUid, raidUid, debt, … } }
```

Событие едет целиком, вместе с дочерними таблицами — заявками, местами по
рейдам, составом, явкой:

```ts
data: {
  title, eventDate, slots, seed, share, status,
  quotas:     [{ raidUid, slots, share }],
  signups:    [{ playerUid, isPriority, raidUid }],  // raidUid — разовый рейд на эту осаду
  roster:     [{ playerUid, source }],
  attendance: [{ playerUid, showedUp, markedAt }],
}
```

Ссылки внутри пакета — по `uid`, не по локальному `id`: у другой машины тот же
рейд может лежать под другим числом.

## Применение чужих изменений

`applyChanges` идёт по сущностям в фиксированном порядке — `class → raid →
player → event` (`APPLY_ORDER`), чтобы к моменту применения события игроки и
рейды, на которые он ссылается, уже были на месте.

Для каждой записи:

1. **Ищем по `uid`.** Нашли — сравниваем `updated_at`: пришедшая запись старше
   локальной → `skipped`, никакого «более раннее значение победило».
2. **Не нашли по `uid` — ищем по естественному ключу** (`family_name`,
   `base_name`+`path`, `name`). Нашли — это та же сущность, заведённая на двух
   машинах независимо (например, сид при установке); локальная строка
   «усыновляется»: получает пришедший `uid`, а старый уходит в `uid_aliases`,
   чтобы ссылки из уже отправленных пакетов продолжали резолвиться.
3. **Удаление** — надгробие пишется всегда, даже если локальной записи не было:
   иначе будущее создание с тем же `uid` не будет знать, что запись уже удаляли.
4. **Событие с неизвестным `raidUid` или `playerUid`** откладывается
   (`deferred`), а не применяется частично: заявка без игрока или квота без
   рейда важнее целостности, чем скорость. Курсор синхронизации не проходит
   мимо отложенной записи (`safeCursor`) — иначе пропущенная ссылка никогда бы
   не дождалась своего рейда или игрока.

**Курсор двигается по данным, а не по числу от сервера.** Клиент запоминает
максимальную ревизию среди записей, которые реально применил, и останавливается
на первой, которую применить не смог. Взять номер, который вернул сервер, —
значит перешагнуть через чужие записи, закоммиченные в ту же секунду.

## Когда срабатывает обмен

Обмен идёт сам, без кнопки:

- при запуске приложения;
- через 30 секунд тишины после последней записи в синхронизируемую таблицу;
- при закрытии окна (с таймаутом, чтобы не держать закрытие бесконечно).

«Грязь» ловится в одном месте — обёртка над `execute()` в
[client.ts](../src/db/client.ts) смотрит на текст запроса и дёргает подписчиков;
звать `touch()` из каждого стора не нужно, и забыть негде. На время применения
чужих правок отслеживание глушится (`withoutTracking`), иначе обмен запускал бы
сам себя по кругу.

**Фоновый обмен молчит при сбоях.** Ошибку показываем только когда человек
нажал кнопку сам; отвалившийся VPN превращается в бейдж в шапке, а не во
всплывашку поверх работы.

## Код подключения

`EASYPL1-<base64url(JSON{url, token})>` — сборка [src/sync/code.ts](../src/sync/code.ts).
Один человек настраивает связку, остальные вставляют код — вводить адрес и
ключ руками не нужно. Секрет здесь тот же `SYNC_TOKEN`, что и на сервере: код
подключения по сути — упаковка пароля, поэтому обращаться с ним как с паролем.

## Секреты и сеть

`SYNC_TOKEN` и `DISCORD_TOKEN` живут только на Worker'е. На компьютерах — только
ключ синхронизации, в диспетчере учётных данных Windows
([src-tauri/src/sync.rs](../src-tauri/src/sync.rs), крейт `keyring`), а не в
базе и не в файле.

Все обращения к серверу идут одной командой Rust — `sync_request(url, path,
payload)`: она добавляет `Authorization: Bearer` и возвращает тело ответа как
есть, разбор и текст ошибок — на стороне Worker'а. Discord-запросы тоже идут
через `sync_request`, а не напрямую из webview: во-первых, там нет прав на
токен бота, во-вторых, CORS всё равно бы не пустил.

## Discord

Импорт заявок по реакциям — [DiscordSignupsModal.vue](../src/components/discord/DiscordSignupsModal.vue)
→ [services/discord.ts](../src/services/discord.ts) → Worker → Discord REST.
Опознание игрока — по `discord_id`, затем по нику (`discord`), затем по фамилии;
неопознанные привязываются вручную и запоминаются.

Привилегированные интенты включаются руками в Developer Portal, не запросом
через ссылку-приглашение:

- без **Server Members Intent** список участников не отдаётся вовсе;
- без **Message Content Intent** текст сообщений приходит пустым — **без
  ошибки**, HTTP 200 и пустая строка вместо содержимого.

Подробный чек-лист настройки — в [sync-worker/README.md](../sync-worker/README.md#сначала--бот-discord).

## Закрытие окна

Ожидание синхронизации при закрытии ограничено таймаутом (`CLOSE_TIMEOUT_MS`
в [stores/sync.ts](../src/stores/sync.ts)) и подстраховано `close()`, если
`destroy()` не прошёл. `core:default` не включает `core:window:allow-destroy` —
без него `preventDefault()` в обработчике навешивал бы окно, которое никогда не
закроется. Разрешение прописано в
[capabilities/default.json](../src-tauri/capabilities/default.json).
